# track.fox.com v2 — Project Context

Factory floor production tracking web app for a manufacturing environment, replacing manually maintained Excel/SharePoint dashboards shown on the floor's digital signage screens. Power BI was evaluated and rejected (on-prem data gateway complexity + OAuth token-refresh incompatibility with the signage players). BrightSign players were the original target but were replaced with a different display solution (2026-09-14); nothing in the app is player-specific, so the pages are referred to simply as "the screens". Owner is a solo IT/infrastructure admin, not a software developer by trade.

## Architecture (locked in)

- Single Python/FastAPI app serves both the backend API and server-rendered frontend (Jinja2 templates + JS polling/charts) — no separate frontend service.
- Deployed via Docker Compose on a single Ubuntu VM, hostname **lost-woods**. No k3s for this project (unlike chat.fox.com / track.fox.com v1).
- Two containers: `app` + `postgres:16-alpine`. Postgres has no exposed host port in production — reachable only over the internal Docker bridge network.
- App connects to Postgres via a dedicated low-privilege role (`trackfox_app`), never superuser.
- **No connection to the plant's ERP database, by decision (2026-09-23).** Every number the app shows is entered by hand through its own forms and stored in its own Postgres. A read-only ERP integration was once planned (connection helper, driver, TODO) and was removed entirely; don't propose bringing it back.
- **lost-woods is a standalone server** — never reference its services via `localhost`; always use hostname or IP.

## Data model (locked in)

- `entries` table: `machine_id, operator, time_slot, units_produced, status, issue, entered_by, entry_date, created_at`. Append-only / history-preserving — never overwrite in place.
- `status` (`:)` / `:(`) is computed at write-time by comparing `units_produced` against a per-machine, per-time-slot cumulative standard in a `standards` reference table.
- 12 fixed time slots: 8AM, 10AM, 12PM, 2PM, 4PM, 6PM, 8PM, 10PM, 12AM, 2AM, 4AM, 6AM. Units are cumulative across each 8-hour shift window.
- **A blank cell means "the number hasn't changed", not "nobody entered it"** (confirmed with the floor 2026-09-03). The crew leaves a checkpoint empty when there is nothing new to write — machine down, operator pulled to another line, waiting on a delivery. So a blank slot produced **zero**, and a blank *first* slot means the counter was still at zero. The Issue column usually corroborates it (C2 read `10500 / 15750 / 15750 / blank` with "OPERADORA MOVIDA PARA WS" logged at 12PM). Consequence: a shift's production is always the **last reading in that shift**, and interior gaps cannot change it. Implemented in `_cumulative_deltas()`, and it applies to **production units only** — since 2026-09-09 scrap is a single shift total with nothing to accumulate against, and downtime never carried forward (a blank there is genuinely unentered, which is what the "no downtime" checkbox on `/console/oee` is for).
- No real authentication — link-based access only: `/dashboard` (public display) and `/console` (entry form, URL-obscurity only, not credentials).
- `entered_by` is a free-text employee number — format-validated but not verified against HR/AD.
- Machines: 37 total, grouped into six dashboard zones (`DASHBOARD_ZONES` in `app/models.py`): `b3`/Combo-FMW (C1–C11, C14–C16), `b2`/FM (FM1–FM3), `ws`/WS (WS1–WS6), `b4`/Poly (P1–P4), `leno`/Leno (AS1–AS7), `pouch`/Pouch (PB1, PB2, PP1). A machine goes in both `MACHINE_IDS` and one zone; an assert at the bottom of `models.py` fails the import if the two disagree. Every page (boards, rounds, `/supervisor`, `/oee`, `/console/oee`, the Pareto picker) builds from those lists, so a new zone needs no page changes. Leno is `AS1`–`AS7`, not `A1`–`A7` — an earlier revision used the short form and those rows were retired in `docs/sql/05_drop_legacy_leno_machine_ids.sql`.
- Standards are **not** uniform across machines, and not even within a group — there are eight distinct per-slot increments across the 37 machines: C1–C5/C14–C16 = 11,700; C6–C11 = 10,800; WS = 9,900; FM = 8,100; P1 = 14,400; P2–P4 = 16,200; AS1–AS5 = 2,520; AS6–AS7 = 2,250. Pouch (PB1, PB2, PP1) = 9,900, the same as WS, but derived the other way: production gave its 100% rate (110 CPM) and the target is 75% of it (see Current state). (An earlier revision of this file claimed the original 23 shared one set of targets; they don't.) Within any machine, its four per-shift checkpoints repeat identically across all three shifts, ramping 1x/2x/3x/4x off the increment.
- A standard is **75% of the machine's theoretical maximum** (confirmed with the floor 2026-09-03). That factor is what the OEE feature's ideal rates are derived from — see `machine_ideal_rates` below.
## CI/CD

Push to `main` → GitHub-hosted runner builds Docker image → pushes to GHCR → self-hosted runner (label `track-fox`, running as unprivileged user `ghrunner` on lost-woods) pulls the image and restarts the `app` container via `docker compose` from `/opt/track-fox-com/`.

- GitHub org: `a-ghost-named-x`, repo: `track.fox.com`.
- Database changes are **not** part of the CI/CD pipeline — they're applied manually via SSH + pgAdmin/psql directly on lost-woods.
- Reference pattern established by existing internal tools: chat.fox.com and track.fox.com v1 (GitHub Actions → GHCR → Docker).

- `/oee` is the Overall Equipment Effectiveness page (added 2026-09-03, moved to shift grain 2026-09-09): OEE = Availability x Performance x Quality, **one row per machine per shift**, plus a downtime Pareto. Follows `/supervisor`'s conventions (no polling, shows every machine, opens on the most recent date *with data*). Read-only. Three shifts, no "All Day". Math and queries in `app/db/oee.py`; the worked example is in its module docstring.
- **OEE data is captured once per shift, not every 2 hours** (floor feedback 2026-09-09). One person enters the whole floor's downtime and scrap at the end of the shift on `/console/oee`; the 2-hour rounds went back to good units only. That split is better for the metric as well as the people — a per-slot delta is the gap between two hand-taken readings, and a reading logged late borrows units from its neighbour, which is what produced false "impossible value" alarms on seven machines in the first week. A shift is 480 minutes however the readings fell. Per-slot OEE columns are gone from `/oee` as a result; the checkpoint sequence lives on the Good column's tooltip.
- `/console/oee` is the end-of-shift form: all 34 machines on one page grouped by zone, each with a per-shift **Scheduled** checkbox, a collapsible downtime picker (11 reason checkboxes with a minutes box each), a **scrap total**, and a note. Every field is pre-filled from what's on record and each write path **skips when nothing changed**, so opening and saving the page doesn't append 34 identical rows. Contrast `/console/<zone>`, which deliberately does NOT pre-fill because several people share it.
- **`/console/oee` must be registered BEFORE `/console/{zone}` in `app/main.py`.** FastAPI matches routes in registration order, so the other way round captures it as a zone named "oee" and 404s. The failure is silent and looks like a missing page. `tests/test_routes_smoke.py` guards it.
- Shift-grain OEE lives in `shift_scrap`, `shift_downtime_entry` + `shift_downtime_reason` (`docs/sql/11_oee_shift_grain.sql`), which supersede the slot-grain `slot_*` tables. `machine_schedule` and `machine_ideal_rates` were already per-machine/per-shift and are unchanged. `entries` and `standards` have never been altered by any of this. Deployment: `docs/deploying-shift-oee.md`.
- The downtime reason codes are **1:1 with the floor's paper downtime form**, in its order. Thirteen active as of 2026-09-24 (`docs/sql/17_new_downtime_reason_list.sql`, after the floor revised the form): Roll Change, Setup, Cleaning (rods, knife, etc.), Equipment Failure, Temperature Adjustment, Delivery, Air Jets Adjustment, Silicon Adjustment, Wicket Hole Adjustment, Registration, Def Material or Misprint, Lack of Material, Lack of Operator. Earlier lists (file 12, then 13's split of Operator Adjustments into four `OPER_ADJ_*`) are retired (`active = false`), not deleted, and past shifts keep them. **A reworded code gets a NEW code, never a rename in place** (user's decision 2026-09-24): `/oee` looks labels up live from `downtime_reasons`, so a rename would rewrite how every past shift reads. The accepted cost is that a 7/30-day Pareto spanning a cutover shows old and new wording as two bars. File 17 sets the active list outright (upsert the 13, retire everything else), so it must be re-run after any re-run of 12 or 13. No per-zone reason list. **All unplanned**, so Planned Production Time is always the full shift. That costs nothing, because planned maintenance on this floor is given a **whole shift**, never part of one — so it is never a downtime reason, it is a machine that wasn't scheduled. The **Scheduled** checkbox on `/console/oee` is the planned-downtime mechanism: unticking it removes the machine from that shift's rollup entirely. The old 10 placeholder codes are `active = false`, not deleted, because migrated history still references them.
- **Shift length (2026-09-16, per-shift since 2026-09-18):** each of a machine's shifts can be set to 8, 10 or 12 hours on `/console/oee`, in `machine_shift_length` keyed (machine, production day, shift) — `docs/sql/14_shift_length.sql` then `15_shift_length_per_shift.sql`. The production manager asked for it because with current staffing one crew often runs a machine 6AM–4PM or 6AM–6PM; the crew keeps writing the running count into the 4PM/6PM boxes on the 2-hour rounds, and OEE was judging those machines against 480 minutes — which is exactly the "beat the maximum" warning WS1/WS2/P1 raised on 9/15. The floor's rules, all in `app/models.py` under "Shift LENGTH": the day **always starts at 6AM**; **a shift's length decides where it starts** — the Nth L-hour shift starts at 6AM + N×L, so a 12h 2nd Shift is always 6PM–6AM and a 10h one 4PM–2AM (stated as fact 2026-09-18; a 12h crew never starts at 2PM); a shift with nothing set **inherits the one before it** (`resolve_day_lengths()`); and **a later shift can be as long or longer than the one before, never shorter** (`shift_length_conflict()` — a shorter one would start inside it and count slots twice). Valid days: 8/8/8, 8/10, 8/12, 10/10, 10/12, 12/12; a 3rd Shift exists only after an 8h or short 2nd Shift (short shifts count as 8h, see below). `shift_slots(shift, hours)` chunks `TIME_SLOTS` (8h reproduces `SHIFT_SLOTS`, asserted at import). The standard scales with the hours (C1 at 12h = 70,200), the downtime cap is the shift's own length (DB CHECK raised to 720), and `/oee` shows an `8h`/`10h`/`12h` label on every row. **The floor screens and the 2-hour rounds are deliberately untouched** — on a machine running long, the 2nd Shift board's colours are meaningless (its 4PM cell holds ten hours of count against a 1x standard) and the floor knows and lives with that. Deployment: `docs/deploying-shift-length.md`.
- **Short shifts (2026-09-23, reworked 2026-10-13):** next to 8h/10h/12h, `/console/oee` takes a typed number of hours, **2, 4 or 6**, per machine per shift (production is only read every 2 hours, so an odd number would end between checkpoints; the box is `step="2"` and the server refuses anything else. The DB CHECK from file 16 still accepts 1–6, which is harmless). Stored in `machine_shift_length.shift_hours` (`docs/sql/16_short_shifts.sql` widened its CHECK). The number is how many hours the machine was **scheduled** for. Mostly Saturdays, where scheduling follows demand and staffing. **A short shift sits inside its normal 8-hour shift**: `pattern_hours()` maps 2/4/6 to 8, so it owns the same four checkpoints the rounds use and counts as 8 for the as-long-or-longer rule (a short 2nd can follow an 8h 1st, not a 10/12h one). Floor facts behind that (2026-10-13): on Saturdays the **2nd Shift always starts at 2PM**, the **3rd (when there is one) always at 10PM**, and the **1st Shift's crew starts at 6, 8 or 10AM but is always done by 2PM**. Every shift can be 2/4/6/8 as needed. The 1st Shift's start time is **deliberately not recorded**: blanks before the crew arrives mean the counter was at zero, blanks after it leaves mean unchanged, so production (the last reading) and PPT (hours × 60) come out the same whenever it started. `shift_span()` therefore says "within 6AM-2PM" for a short 1st Shift instead of inventing a clock time; a short 2nd/3rd is an exact span ("2PM-8PM", "10PM-2AM"). The one inexactness: while a late-starting 1st Shift is still running, its elapsed PPT counts from 6AM (harmless, since OEE needs end-of-shift downtime). *History:* the first version (9/23) put short days on a **6-hour pattern** (1st 6AM–12PM, 2nd 12PM–6PM, 3rd 6PM–12AM). The floor never runs a 12PM 2nd Shift, so a real 2PM–8PM crew was read from the 2PM/4PM/6PM boxes, lost its 8PM reading to an unscheduled 3rd Shift, and read about a third low. Dropping the pattern needed no SQL; it re-reads every short 2nd/3rd Shift entered since 9/23 on the right window (short 1st Shifts keep their numbers unless something was written in their 2PM box). What's *inherited* is the pattern: after a short shift the next one is a full 8h. **Scheduled defaults** (`default_scheduled(shift, day_lengths)`, which takes the whole resolved day): the 1st Shift yes; a later shift only if it **and every shift before it** are exactly 8h. So after a short shift every later shift starts unticked, even an 8h one (on those days not every crew runs); picking a non-8 length on the 2nd/3rd page ticks it via JS, a full 8h crew is ticked by hand. `/console/oee` shows why on the Scheduled box (`_unticked_hint()`), and `/oee` gets a `short_day` flag per machine-shift for its tooltip. The 3rd Shift page has a length control (8h or short) whenever the 3rd Shift exists. The hours are **scheduled time, not time run** — a no-show inside them is Lack of Operator, and the form says so; typing fewer hours would erase the loss the way unticking Scheduled does. Each crew starts its count from zero. A "Set every machine to N hours" button fills the form for a Saturday. There is **no automatic Saturday default** on purpose: forgetting leaves 8h, which understates OEE rather than inflating it.

## Key gotchas learned the hard way

- `docker-entrypoint-initdb.d` scripts only fire on a fresh volume; schema/seed SQL must be applied manually against an existing volume.
- `docker compose up -d` won't recreate unchanged containers — use `--force-recreate` (e.g. `sudo docker compose up -d --force-recreate db`).
- `python:3.12-slim` once silently rolled to Debian 13 (trixie) under a floating tag and broke a third-party apt install. The image is pinned to `python:3.12-slim-bookworm`. The package that broke was removed 2026-09-23 (only `tzdata` is apt-installed now), so the pin no longer has a hard reason and could move to trixie, but do that as its own change and test the build.
- `docker/build-push-action` cache requires `docker/setup-buildx-action@v3` (switches from the `docker` driver to `docker-container` driver) for cache export to work.
- Self-hosted runner runs as a dedicated unprivileged account (`ghrunner`), not a personal admin account.
- pgAdmin: disable SSL mode when connecting to a Postgres container that has no SSL configured, or you'll get connection errors.
- **This project uses pgAdmin, so every `.sql` file here must be plain SQL.** psql meta-commands (`\set`, `\i`, `\echo`) and psql variable interpolation (`:'name'`) are client-side features — pgAdmin sends the backslash straight to the server and it fails with `syntax error at or near "\"`. Parameterise with a one-row `WITH target AS (SELECT DATE '...' )` CTE instead. (`-v ON_ERROR_STOP=1` is fine; it's a command-line flag, not file content.)
- **pgAdmin shows only the LAST result set** when you execute a file with several statements. A diagnostic file whose useful output is in queries 1–4 will appear to return nothing at all. Run those queries one at a time, and don't put verification `SELECT`s after the thing they verify and expect them to be seen.
- A `standards` row of `standard_units = 0` is far more dangerous than a *missing* row. Missing raises `StandardNotFoundError` and `/console` visibly marks the row failed; zero saves silently and, because `compute_status()` is `units_produced >= standard_units`, makes the cell permanently green. Placeholder seed files must never be applied with their zeros still in them.
- `trackfox_app` has only `GRANT SELECT ON standards` by design — seed scripts must be run as the `postgres` superuser, not the app role. Same for `downtime_reasons` and `machine_ideal_rates`.
- **Never put a second writer's column on `entries`.** `get_latest_entries_for_date()` resolves the grid with `DISTINCT ON (machine_id, time_slot) ORDER BY created_at DESC` — the newest **row** wins wholesale. Scrap on `entries` would mean the scrap person's submission becomes the newest row for that cell and blanks the units the production person entered minutes earlier, taking the floor screens down. That single fact is why OEE got its own tables.
- **Retiring a reason code silently deletes its minutes on the next correction — unless the form carries it forward.** `/console/oee` pre-fills from the record, the picker lists only active codes, and the newest downtime header wins wholesale. Put those together and re-saving a pre-retirement shift for *any* reason (fixing the note, correcting a different reason) posts only what the form could see, and the retired code's minutes fall off that shift. Latent since file 12 retired the placeholders, armed by file 13 retiring `OPER_ADJUST` with live data behind it. Fix: a retired code is rendered on a machine's row only when that shift already has it (`_retired_on_row()` in `app/routers/console_oee.py`, tagged "retired"), `_collect_reasons()` reads the form against the full table, and `create_shift_downtime()` rejects only codes that don't exist at all. Any future retirement gets this for free; `tests/test_routes_smoke.py` guards it.
- **A downtime submission with zero reasons is not the same as no submission.** The first says "ran clean, 100% availability"; the second says "nobody has entered this yet". Collapsing them would default missing data to a perfect score — the `standard_units = 0` trap one layer up. That's why downtime is a header table plus children rather than a nullable column pair.
- **Rolling OEE up across machines requires a capacity-weighted Availability**, not `run_minutes / ppt_minutes`. With 8 different ideal rates on the floor, clock-time availability makes a zone's `A x P x Q` multiply out to something that isn't its OEE, because a minute on AS1 (1,680/hr) isn't worth a minute on C1 (7,800/hr). For a single machine the two definitions are identical. `tests/test_oee_math.py` asserts the identity at both levels — it's what caught this.
- **Pydantic's `ValidationError` is a subclass of `ValueError`.** A bare `except ValueError` placed *before* `except ValidationError` silently swallows validation failures and mislabels them as bad number formatting. Order the specific case first (see the write paths in `app/routers/console.py`).
- **The shift-length radio group needs no presence marker, but only because one option is always rendered checked.** A radio group whose control was on the page always posts its value; absence in the POST can therefore only mean the control wasn't rendered (a 3rd Shift row that doesn't exist after a 10/12h 2nd), and is read as "leave it alone". If the default-checked option were ever removed, this would silently become the same absent-vs-unticked trap the Scheduled checkbox has. **That is why the short shift is a fourth radio (`value="short"`) with the number box inside it, not a free-standing number input** — and the box only counts when that radio is picked. A number in the box beside 8h/10h/12h is refused as a contradiction (`_parse_length()` in `app/routers/console_oee.py`), the same rule as minutes typed against an unticked reason; the JS picks the radio on typing (on `input`, not `focus`, so tabbing through doesn't switch a machine to an empty short shift) and clears the box when another length is picked.
- **On a short shift the minutes are NOT its checkpoints × 120.** It owns its 8-hour shift's four slots but is scheduled for `hours` of it, so PPT is `min(elapsed slots × 120, hours × 60)` and `shift_minutes` is `hours × 60`. For 8/10/12 the two formulas agree, which is exactly why the old `SLOT_MINUTES * len(slots)` looked right. Anything new that computes a shift's minutes must use the hours.
- **Each OEE table is read by ONE query, over a date range** (`get_shift_lengths_for_range`, `get_downtime_for_range`, `get_schedule_for_range`, `get_scrap_for_range`, plus `get_readings_for_range` in `app/db/entries.py` for production); the one-day OEE readers are thin wrappers keyed without the date. `get_latest_entries_for_date()` was deliberately **not** turned into a wrapper, because it feeds the floor screens. The 7/30-day view can't call `compute_oee_report()` per day — `get_pg_connection()` opens a fresh connection per query, and 30 days plus the 30 before would be ~500 connections. Tests stub the one-day readers for the report and the range readers for `compute_oee_range()`; a new reader of either kind needs its stub in both `tests/test_oee_report.py` and `tests/test_routes_smoke.py`, or it reaches for a real database.
- **"Absence means scheduled" is no longer a universal default — it depends on the shift length.** `machine_schedule` still stores only exceptions, but the value a missing row stands for comes from `default_scheduled(shift, hours)`: True for any 8h shift, False for a 10/12h 2nd Shift. Every reader (`compute_oee_report`, `_existing_rows` on the form) must go through that function, or the form's "skip when unchanged" check and the report disagree about whether a ticked box is a change. **And the default can flip within one save:** picking 12h on the 2nd Shift page changes that shift's default from scheduled to not-scheduled, so the POST compares the submitted tick against `default_scheduled(shift, submitted_hours)` — not against what the box showed when the page loaded — or a tick made on the same save looks unchanged, is never written, and the night shows as not scheduled on the next load. `_existing_rows` carries `scheduled_explicit` so the POST knows whether it's comparing against a real row or a default.
- **The date on the review side and the date on the rounds are one day apart for night slots, on purpose.** A 12AM–6AM checkpoint is filed by `/console/<zone>` under the morning's date and shown by `/oee`, `/supervisor` and `/console/oee` under the evening's. Any new reader of `entries` for a review page must use `get_production_day_entries()` (or `shift_slot_dates()`), not `get_latest_entries_for_date()` with the review page's date — the latter silently returns the *previous* night's 12AM–6AM readings.
- **An unticked checkbox and an absent one are indistinguishable in a form POST** — neither appears in the body. For the Scheduled checkbox that ambiguity was dangerous: reading absence as "unticked" marked every machine not on the submitted form as not-scheduled, removing them from the OEE denominator and inflating every number. Fixed with a hidden `sched_present_<machine>` companion field the browser always posts.
- **Treating a blank checkpoint as "unknown" silently flatters OEE.** Blanks are a machine's *worst* slots — that's why they're blank — so dropping them removes exactly the bad hours from the calculation. C2's real row scored 33.7% when its trailing blank was excluded and 25.2% once it counted as zero, and the second is the truth. Worse, `blank / 15750 / blank / blank` used to yield *nothing at all*, since the 10AM delta had no baseline. Any future change here must keep the two guards in `_cumulative_deltas()`: an entirely unreported shift stays unknown, and un-elapsed slots stay unknown.
- **A per-slot delta is not a measurement of the machine — it's the gap between two hand-taken readings.** (This is now moot for OEE, which is captured per shift, but it is exactly WHY it is.) Checkpoints aren't logged exactly on the slot boundary, so a late reading borrows units from its neighbour. Real first-day data: WS1 ran `14225 / 7538 / 13438 / 12442` and C8 ran `19500 / 0 / 6000 / 600`, while finishing the shift at 90% and 45% of their ceilings respectively. **Never judge a machine on one slot's delta.** Four slots are 480 minutes no matter when each reading was taken, so anything comparing against capacity belongs at shift level (`_machine_warnings()` in `app/db/oee.py`) — and only once a *majority* of the shift's slots are countable, or a sparse day (AS4 reported 8AM and 12PM with 10AM missing, leaving one countable slot) just reproduces the same single-delta judgement under a different name.
- **Don't let a derived number accuse the floor's measured number.** `/oee` originally hard-excluded any slot over `standard / 0.75` as "more units than the machine can physically make in 2 hours". On the first real day it fired on seven machines (C7, C8, WS1, WS2, WS5, P4, AS4) — six of them on the 8AM slot — discarded genuine production and blamed the floor, when what was actually wrong was a per-slot test applied to timing noise. The ceiling is derived from an unverified 75% assumption and is the *less* trustworthy of the two numbers. Now: over the ceiling warns only at shift level and still counts; only past `IMPLAUSIBLE_CEILING_MULTIPLE` (2x) is a slot treated as a typo and excluded. `docs/sql/10_diagnose_over_ceiling.sql` diagnoses it; query 3 there prints the raw checkpoint sequence, which is what actually revealed this.
- **A bad checkpoint's damage depends on WHERE it is.** A cumulative value typed too low makes its own delta negative and the next one huge as the counter recovers. At shift grain that mostly doesn't matter: a shift's production is its LAST reading, so a mid-shift typo warns (`units_went_backwards`) but the total is still right and the machine still counts. Only a *final* reading below an earlier one actually corrupts the total — that's `final_reading_low`, and it's the one that excludes. See `_summarise_production()`.
- OEE is computable from **good units + downtime alone** — scrap cancels out of `A x P x Q`. So a slot missing its scrap still yields a real OEE with Performance and Quality as N/A, rather than being discarded. Don't "simplify" that into all-or-nothing.
